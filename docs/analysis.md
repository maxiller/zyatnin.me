# Анализ проекта zyatnin.me

## 1. Назначение и метод анализа

Документ фиксирует фактическое состояние проекта `zyatnin.me` на момент анализа и служит исходной точкой для дальнейшей разработки. Анализ выполнен по исходному коду репозитория, конфигурации сборки, шаблонам, данным локализации и результатам реальной сборки. Все выводы, помеченные как дефект, подтверждены либо чтением исходников, либо собранным HTML в каталоге `_site`.

Метод анализа:

1. Инвентаризация файлов, маршрутов и зависимостей.
2. Чтение конфигурации Eleventy, шаблонов, JSON-данных и стилей.
3. Сборка проекта командой `npm run build` и проверка сгенерированного HTML.
4. Сопоставление фактического поведения с ожидаемым для портфолио и блога.
5. Оценка нефункциональных характеристик и рисков.

Требования, вытекающие из анализа, формализованы в [SRS](SRS.md).

## 2. Краткое резюме

`zyatnin.me` — статический персональный сайт-портфолио с блогом на трёх языках (русский, английский, иврит). Сайт собирается генератором Eleventy 3 из Markdown- и Nunjucks-шаблонов, не имеет серверной части и публикуется на GitHub Pages по пользовательскому домену `zyatnin.me`.

Сильные стороны:

- Простая и прозрачная архитектура без лишних зависимостей.
- Полноценная трёхъязычная модель с корректной разметкой `lang` и `dir`, включая RTL для иврита.
- Продуманная визуальная система на CSS-переменных с тёмной и светлой темами.
- Адаптивная вёрстка с брейкпоинтами 768 и 480 пикселей.
- Безопасная модель распространения: статический хостинг, отсутствие секретов и трекеров.
- Автоматический деплой через GitHub Actions.

Критические проблемы:

- Даты публикаций отображаются пустыми или в неверном формате.
- Мобильное меню не открывается из-за рассинхронизации имени CSS-класса.
- Мета-описание статей игнорирует поле `excerpt` и подставляет общий текст сайта.
- Часть CSS-классов в шаблонах не имеет определений, а часть определений не используется.
- Контраст акцентного цвета на светлом фоне ниже требований WCAG AA.
- Контент главной и индекса блога скрыт при отключённом JavaScript.

## 6. Архитектура сборки и рантайма

```mermaid
flowchart TD
    C["Контент-файлы: метаданные + три языковые ветви"] --> LIB["lib/content.js: разбор, проверки, URL"]
    LIB --> E["Eleventy 3"]
    NJK["Nunjucks-шаблоны"] --> E
    JSON["JSON-данные локализации"] --> E
    DATA["Directory data и contentModel.js"] --> E
    ASSETS["assets: CSS и JS"] -->|passthrough| OUT["_site"]
    CNAME["CNAME"] -->|passthrough| OUT
    E --> HTML["HTML-страницы"]
    HTML --> OUT
    OUT --> CI["GitHub Actions"]
    CI --> PAGES["GitHub Pages"]
    PAGES --> USER["Браузер посетителя"]
```

Ключевые архитектурные решения:

- **Одна страница — один файл.** Метаданные страницы пишутся во front matter один раз, переводимые сущности — в кусте `translations` и в трёх разделах тела с маркерами `<!-- lang:xx -->`. Из одного файла генерируются страницы всех трёх языков, поэтому общее поле (статус проекта, метки, дата публикации) нельзя рассинхронизировать между языками.
- **Модель контента в одном модуле.** `lib/content.js` разбирает файлы, проверяет их (неизвестные поля, отсутствие или дубль языковой ветви, `slug` ≠ имя файла, словарь меток, длина `excerpt`, дубли `order`), применяет правило публикации из `lib/published.js` и выводит URL каждой страницы. Ошибка останавливает сборку до Eleventy (через `scripts/check-content.js`).
- **Страницы генерируются, а не лежат файлами.** `src/content-page.njk` пагинирует по `contentModel.pages` (`src/_data/contentModel.js`), а `src/content-page.11tydata.js` раскладывает выбранную языковую ветвь в обычные данные страницы — макеты (`layouts/post.njk`, `layouts/project.njk` и их dev-версии) не знают, что страница собрана из контент-файла.
- **Мультиязычность через структуру каталогов шаблонов.** Языковые главные, индексы блога и страницы меток лежат в `src/{lang}`; файл `{lang}.11tydata.js` подмешивает соответствующий JSON в переменную `i18n` для страниц этого каталога; сгенерированные страницы получают `i18n` своей ветви из `content-page.11tydata.js`.
- **Отдельные коллекции для каждого языка.** `posts_{lang}`, `projects_{lang}` и `tagPages_{lang}_{view}` собираются из модели и отдают шаблонам тот же набор полей, что раньше отдавали файлы-страницы.
- **Единый каркас.** Все страницы используют `layouts/base.njk` (вид «Лидер») или `layouts/dev/base.njk` (вид «Инженер»), которые задают `lang`, `dir`, метаданные, шапку, подвал и подключают ресурсы.
- **Маршрутизация без полей в контенте.** URL страницы выводится из `view` и `slug`; полей `permalink` и `layout` в контент-файлах нет, поэтому URL не может разойтись с содержимым.
- **Пасстхру-копирование.** Каталог `src/assets` и файл `CNAME` копируются в корень сборки без обработки.
- **CSS-переменные как дизайн-токены.** Светлая и тёмная темы закреплены за видами и реализованы через `:root` в `style.css` и `dev.css`.

### 7.1 Контент-файл страницы

Страница существует в одном экземпляре — файле `content/posts/<slug>.md` или `content/projects/<slug>.md`. Front matter содержит только метаданные, одинаковые для всех языков:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `slug` | строка | Имя файла; вместе с `view` задаёт URL |
| `view` | строка | `leader` или `dev` — вид, в котором видна страница; задаёт также макет |
| `date` | дата | Только пост: сортировка, отображение и дата публикации; будущая дата — отложенная публикация |
| `tags` | массив | Только пост: от одной до трёх меток из словаря `tags.names`; ключи общие для всех языков и ведут на страницы меток `/{lang}/tags/{tag}/` и `/{lang}/dev/tags/{tag}/` |
| `order`, `icon`, `status` | число, строка, строка | Только проект: позиция карточки, эмодзи, статус `done`/`in_progress` |
| `draft`, `updated` | boolean, дата | Необязательные: черновик и дата обновления |

Переводимые сущности лежат в кусте `translations.ru` / `.en` / `.he` (для поста — `title`, `excerpt`, необязательные `description`, `cover`; для проекта — `title`, `excerpt`, `tags`, необязательные `points`), а тело страницы — три раздела Markdown, открывающихся маркерами `<!-- lang:ru -->`, `<!-- lang:en -->`, `<!-- lang:he -->`. Полная схема с примерами — в [SRS, раздел 7.1](SRS.md#71-контент-файл-страницы).

> **Обновление 2026-11-12.** До 1.18 страница существовала тремя файлами (`src/{lang}/posts/<slug>.md`), и общее поле приходилось править трижды: статус проекта, метки и дату публикации держали в трёх копиях, между которыми не было автоматической сверки. Теперь 162 файла статей и 9 файлов проектов сведены к 54 и 3 файлам, а поля `layout` и `permalink` из контента удалены — они выводятся из `view` и `slug`. Проверку модели выполняет `lib/content.js`, страницы генерирует `src/content-page.njk`.

### 7.2 Метки

Категории-топики удалены: тематику статьи выражают метки в поле `tags` метаданных (от одной до трёх), поэтому они одинаковы во всех трёх языках статьи по построению, а не по договорённости. Подписи меток лежат в `tags.names` языковых JSON и переведены на все три языка; ключи — латиница вида `[a-z0-9-]+`. Для каждой тройки «язык × вид × встреченная метка» при сборке генерируется страница метки со списком статей (`lib/content.js`, коллекции `tagPages_{lang}_{view}`), поэтому метка всегда кликабельна и не ведёт на несуществующий адрес. Сборка падает, если у статьи не 1–3 метки или ключа нет в словаре.

### 7.3 Данные проектов

Контент проектов хранится в `content/projects/*.md` в том же формате, что и статьи. Метаданные: `slug`, `view`, `order`, `icon`, необязательный `status` (`done`/`in_progress`). Переводимые поля каждой ветви: `title`, `excerpt`, `tags` (отображаемые подписи технологий, а не ключи словаря меток) и необязательный `points` — ключевые результаты, которые выводятся списком в карточке и на странице. Карточки на главной рендерятся из коллекции `projects_{lang}` и сортируются по `order`, поэтому имя, описание и теги проекта существуют в одном экземпляре на страницу, а не на язык. Схема — в [SRS, раздел 7.1](SRS.md#71-контент-файл-страницы).

Скрипты `package.json`:

| Скрипт | Команда | Назначение |
| --- | --- | --- |
| `build` | `check-content.js && clean.js && eleventy && check-seo.js` | Сборка в чистый `_site` с проверками |
| `build:ghpages` | то же | Используется в CI |
| `clean` | `node scripts/clean.js` | Удаляет `_site` |
| `start` | `eleventy --serve --port=5000` | Локальный сервер (предпросмотр; пишет `[preview]`) |
| `dev` | `eleventy --serve --port=5000` | Идентичен `start` |

> **Обновление 2026-11-12.** Сборка начинается с очистки `_site` (`scripts/clean.js`, SRS FR-90): Eleventy не удаляет файлы, которых больше нет в сборке, а предпросмотр (`--serve`) пишет в тот же каталог отложенные статьи и черновики. До этого любой `npm start` оставлял в `_site` 66 лишних страниц, и следующий `npm run build` падал на самопроверке SEO. Отдельно режим предпросмотра теперь называет себя строкой `[preview]` в логе (FR-91).

> **Обновление 2026-11-09.** В потоке появились два новых шага: сайт пересобирается также по расписанию (`schedule: cron: 0 3 * * *` в `deploy.yml`, SRS FR-124) — без этого отложенные статьи не появились бы никогда, а в самой сборке директива `eleventyComputed` из `src/{lang}/posts/posts.11tydata.js` решает, что из `src/{lang}/posts/*.md` писать в `_site` и что отдавать в коллекции (FR-123). Запуск через `--serve` и переменная `INCLUDE_FUTURE=1` обходят шлюз для предпросмотра; с 1.18 шлюз живёт в `lib/content.js` и срабатывает при чтении контент-файла.

Фактическая проверка: `npm install` установил 114 пакетов, `npm run build` собирает 232 файла (224 HTML-страницы) за 0,42 секунды вместе с тремя проверками. Сборка проходит без ошибок.

### 10.1 Сводная таблица

| ID | Дефект | Серьёзность | Подтверждение |

### 10.2 Q-01: даты публикаций

Фильтр `dateDisplay` в `.eleventy.js`:

```js
eleventyConfig.addFilter("dateDisplay", (dateStr) => {
  if (!dateStr) return "";
  return String(dateStr).split('T')[0].substring(0, 10);
});
```

YAML-дата `2026-03-05` разбирается как объект `Date`. Проверка через `gray-matter` подтверждает: `typeof date === "object"`, `date instanceof Date === true`. При преобразовании `Date` в строку получается `"Thu Mar 05 2026 00:00:00 GMT+0000..."`. Дальнейшее поведение зависит от дня недели:

| Дата | Результат фильтра |
| --- | --- |
| `2026-03-05` (четверг) | пустая строка |
| `2026-03-15` (воскресенье) | `Sun Mar 15` |
| `2026-02-15` (воскресенье) | `Sun Feb 15` |
| `2026-01-28` (среда) | `Wed Jan 28` |
| `2026-03-10` (вторник) | пустая строка |

В собранной статье: `article__meta"> · 2 мин. чтения`. В индексе блога часть карточек содержит `Sun Mar 15`, часть — пустой `<span></span>`. Сортировка при этом работает корректно, потому что выполняется по объектам `Date`.

Причина: фильтр рассчитан на строку ISO 8601, а получает объект `Date`. Исправление должно нормализовать дату и форматировать её с учётом языка (`Intl.DateTimeFormat`).

### 10.3 Q-02: мобильное меню

CSS определяет открытое состояние как `.mobile-menu.open` (`style.css`, строка 361). JavaScript добавляет и удаляет класс `mobile-menu--open` (`app.js`, строки 32 и 38). В результате при нажатии на гамбургер атрибут `aria-expanded` меняется, но меню остаётся `display: none`. На экранах до 768 пикселей навигация по секциям главной страницы недоступна.

### 10.4 Q-03: мета-описание статей

`base.njk` использует переменную `description`:

```njk
<meta name="description" content="{% if description %}{{ description }}{% else %}Max Zia — IT Engineer...{% endif %}">
```

Статьи задают `excerpt`, а не `description`. В результате все страницы статей получают одинаковое общее описание. Это ухудшает сниппеты в поиске и социальные превью.

### 10.6 Q-06: контрастность

Расчёт по формуле WCAG для относительной яркости:

| Пара | Контраст | Норма 4.5:1 | Вывод |
| --- | --- | --- | --- |
| `--accent` `#0ea5e9` на `--bg` `#f5f4f0` | 2.52 | Нет | Не проходит даже 3:1 |

### 10.8 Q-08: паритет локализации

Три JSON-файла (`ru.json`, `en.json`, `he.json`) поддерживаются вручную. На момент анализа паритет соблюдён: по 38 ключей в каждом файле и по 12 статей в каждом языке, длина `excerpt` составляет от 42 до 111 символов. Однако автоматической проверки нет: любое добавление ключа только в один файл приведёт к пустому тексту в соответствующем языке без ошибки сборки. Аналогично нет проверки, что у каждой статьи есть переводы во всех трёх каталогах.

### 10.9 Q-09: воспроизводимость сборки

`package-lock.json` находится в `.gitignore`, CI выполняет `npm install`, а не `npm ci`. Диапазоны версий `^3.1.2` и `^14.1.0` допускают обновление минорных версий. Сборка не воспроизводима побайтово и подвержена риску неожиданных изменений зависимостей.

### 10.10 Q-10: отсутствие контроля качества

В проекте нет:

- unit-, интеграционных или e2e-тестов;
- ESLint, Stylelint, Prettier;
- проверки внутренних ссылок;
- HTML-валидации;
- Lighthouse CI или аналогичной проверки.

### 10.11 Q-17: зависимость отображения от JavaScript

Стили задают скрытие элементов с классом `.fade-in`:

```css
.fade-in {
  opacity: 0;
  transform: translateY(20px);
}
```

Класс видимости добавляет только `app.js` через `IntersectionObserver`. Если JavaScript отключён, заблокирован или `IntersectionObserver` недоступен, секции главной страницы, карточки проектов и карточки статей блога остаются с `opacity: 0`, то есть невидимыми. Это противоречит принципу прогрессивного улучшения и ухудшает доступность и индексацию.

Исправление: по умолчанию контент должен быть видимым, а анимация должна включаться только при наличии JavaScript (например, через класс `js` на `html`) и отключаться при `prefers-reduced-motion`.
