# Черновик статьи и публикация

Поток из двух шагов: сначала текст на согласование, потом — по явному подтверждению — финальный вариант и публикация. Ни один шаг не перескакивается: черновик не коммитится и не пушится, финал не пишется без подтверждения.

Скилл описывает страницу сайта: статью (`content/posts/<slug>.md`), а для проекта — тот же поток с `content/projects/<slug>.md` и правилами проектов из `content-maker`. Если пользователь просит текст, который не становится страницей сайта, выполняется только раздел 1 — без контент-файла, коммита и пуша.

## 1. Черновик

Вход — тема и требования пользователя. Выход — русский текст статьи в ответе (Markdown), без файлов в репозитории.

Перед текстом коротко зафиксируйте решения, которые пользователь подтверждает вместе с черновиком:

- `slug` — `[a-z0-9-]+`, станет именем файла и частью URL;
- `view` — `leader` (управление, процессы, люди, клиентский успех) или `dev` (техника, инструменты, разработка); правило выбора — в skill `content-maker`;
- `tags` — 1–3 ключа из `src/_data/i18n/*.json` → `tags.names`, самый точный первым;
- `date` — дата публикации; уточните, нужна ли публикация сегодня или отложенная (будущая дата держит статью вне сборки, FR-123);
- `title` и `excerpt` на русском: `excerpt` — 40–200 символов, без HTML.

Требования к тексту:

- Русский язык, первое лицо, личный опыт, без канцелярита; термины (ITIL 4, KCS, Shift Left) поясняются при первом употреблении.
- Разделы — только `##` и `###`, каждый — законченная мысль; H1 не нужен, заголовок берётся из `title`.
- Объём: стратегическая статья 1400–1800 слов, операционная 1000–1400.
- Таблицы — markdown с шапкой; списки короткие, без вложенности глубже двух уровней; кавычки-«ёлочки», длинное тире, без HTML-сущностей.
- **Не выдумывать факты и цифры.** Место, где нужны данные автора, помечайте `<!-- вилка: … -->` и перечислите все вилки отдельным списком после текста.
- Ссылки — только на существующие страницы сайта. Соседние ещё не вышедшие статьи упоминайте текстом, не ссылкой (FR-128).
- 1–3 схемы `mermaid` — только там, где картинка несёт идею (цикл, развилка, обзор понятий). Разметка — по [prompt-finalize-article.md, раздел 3](../../../articles/prompt-finalize-article.md#3-схемы-mermaid): `flowchart TD` или `mindmap`, подписи в кавычках, только классы `:::good` / `:::bad` / `:::neutral`, без `classDef`, `style` и `%%{init}%%`.
- Без front matter и без переводов: черновик — это только русский текст и решения из шапки.

Черновик показывается целиком в ответе (не файлом и не страницей сайта): контент-файл требует сразу трёх языков и валидных метаданных, иначе падает сборка (FR-85, FR-125). Файл `content/posts/<slug>.md` с `draft: true` — не способ показать текст на согласование: это готовая скрытая страница, её создают только по отдельной просьбе.

## 2. Подтверждение

Завершите ответ явным вопросом о публикации и перечислите последствия: будут добавлены ветви `en` и `he`, обложки, статья попадает в репозиторий, коммит уходит в `main` и сайт публикуется (или встаёт на дату).

- Продолжайте только после явного «да» / «публикуй». Молчание, правки и уточнения — не подтверждение.
- Пользователь правит текст — внесите правки, покажите изменённое и спросите снова.
- Пользователь просит только текст без сайта — не создавайте контент-файл, не коммитьте и не пушите.

## 3. Финал по спецификации

После подтверждения прочитайте [articles/prompt-finalize-article.md](../../../articles/prompt-finalize-article.md) целиком и выполните его: это спецификация финального варианта. Правила контента, языков и меток — skill `content-maker`.

Коротко, что обязательно войдёт в файл `content/posts/<slug>.md`:

- метаданные (`slug`, `view`, `date`, `tags`) — один раз; `layout` и `permalink` не пишутся;
- `translations.ru/en/he` с `title` и `excerpt` в допустимых пределах;
- три раздела тела с маркерами `<!-- lang:ru -->`, `<!-- lang:en -->`, `<!-- lang:he -->`; структура, таблицы и схемы совпадают во всех языках, подписи схем переведены;
- если статья входит в серию — обновление её README (для серии лида — `articles/leader-strategy/README.md`).

Проверки до коммита:

```bash
npm run covers:svg   # исходники обложек из заголовка, даты и меток; исходники коммитятся
npm run build        # модель контента, шаблоны, SEO, ссылки, метаданные
```

Модель статьи (подставить `slug`) должна вернуть три строки:

```bash
node -e 'const c=require("./lib/content");const s=process.argv[1];const p=c.load().pages.filter(x=>x.slug===s);if(p.length!==3)throw new Error("ожидались 3 страницы, получено "+p.length);console.log(p.map(x=>x.lang+" "+x.url+" — "+x.title).join("\n"))' <slug>
```

Если в статье есть схемы, проверьте их в предпросмотре `npx eleventy --serve --port=5010`: без тёмной плашки, узлы окрашены классами, подписи читаются, схемы не шире колонки.

## 4. Коммит и пуш

Подтверждение публикации — это и есть разрешение на коммит и пуш в `main`; без него шаг не выполняется. Пуш в `main` запускает деплой на GitHub Pages.

1. Проверьте, что вы на ветке, которая деплоится, и что удалённый репозиторий — тот самый:

```bash
git branch --show-current   # main
git remote -v               # origin → github.com/maxiller/zyatnin.me
```

2. Добавьте в индекс только файлы статьи и её обложек (плюс README серии, если менялся):

```bash
git add content/posts/<slug>.md covers/<slug>-ru.svg covers/<slug>-en.svg covers/<slug>-he.svg
git status --short
```

`_site/` и `src/assets/covers/*.png` в коммит не попадают — они генерируются сборкой.

3. Коммит — в принятом в репозитории формате, с русским заголовком статьи:

```bash
git commit -m 'content: article "<русский title>"'
```

4. Пуш:

```bash
git push origin main
```

## 5. Проверка публикации

Пуш не считается выполненным, пока деплой не проверен. Загрузите skill `check-action-on-push` и выполните его шаги для отправленного коммита (не для «последнего вообще»):

```bash
SHA=$(git rev-parse HEAD)
gh run list --commit "$SHA" --limit 5 --json databaseId,status,conclusion,workflowName,headSha
gh run watch <databaseId> --exit-status --interval 10
```

После успешного workflow проверьте, что страница действительно отдаётся сайтом, а не только собралась:

```bash
for lang in ru en he; do
  curl -sS -o /dev/null -w "$lang %{http_code}\n" "https://zyatnin.me/$lang/blog/<slug>/"
done
```

Для вида `dev` путь — `https://zyatnin.me/<lang>/dev/blog/<slug>/`. GitHub Pages обновляется не мгновенно после успеха workflow: при 404 подождите и повторите, не создавая новый коммит. Полезно убедиться, что в HTML есть заголовок статьи.

В итоговом сообщении укажите: коммит и SHA, номер и ссылку запуска workflow, три URL статьи и их коды ответа, оставшиеся вилки. Если `date` в будущем, страницы сейчас не будет по устройству сайта (FR-123): скажите, с какой даты она появится и что проверка «опубликовано» на этот момент невозможна.

## Стоп-условия

- Сборка падает — коммита и пуша нет; чините причину, а не проверки.
- Нет явного подтверждения — нет контент-файла, коммита и пуша.
- Не выдумывайте данные вместо вилок: перечислите их в отчёте.
- Не трогайте шаблоны, стили, `app.js`, `.eleventy.js`, `lib/` ради статьи: нужен новый цвет или стиль схемы — это отдельное изменение дизайна и SRS.
- Не выполняйте `gh run rerun`, `gh run cancel` и `workflow_dispatch` без просьбы.
